# 应用升级设计与实现

日期：2026-09-12

状态：设计已审核修正，功能已实现；签名发布与真实安装覆盖验收见第 7 节。

## 1. 审核结论

保留「同一更新清单，安装版应用内升级，便携版手动下载」的架构。修正以下问题：

| 原设计问题 | 修正 |
| --- | --- |
| 声称 NSIS exe 不能直接用于升级，必须 `.nsis.zip` | 本项目使用 Tauri 2；`createUpdaterArtifacts: true` 直接生成 `*-setup.exe` 和 `.exe.sig`。zip 属于 v1Compatible 模式，不采用 |
| 假设插件静默安装完成后返回，再由前端 relaunch | 明确使用 passive 模式。Windows 插件启动安装程序后退出当前进程，NSIS 完成覆盖后负责重启；移除 process 插件与前端重启调用 |
| 通过 LocalAppData/Programs、Program Files 前缀判断安装版 | Tauri currentUser 默认位置实际为 LocalAppData/产品名，且支持自定义路径。改为核对当前用户 NSIS 卸载注册项、当前 exe 与卸载文件；识别失败走手动下载 |
| 安装入口重新检查 latest，且未在 Rust 拒绝便携版 | Rust 缓存已检查的 Update，安装请求必须匹配所展示的版本；重新校验安装形态，不接受前端传入包地址或签名 |
| 没有处理活动任务、未保存修改及重复点击 | 安装前检查未保存文档和文件操作，Rust 阻止活动任务期间安装，安装与新任务启动互斥；检查和安装均单飞 |
| 将 updater 默认权限开放给前端 | 前端仅调用自定义 Rust command，移除直接 updater IPC 权限，避免绕过安装保护；opener 只允许固定下载页 |
| 声称未配置私钥仍会成功发布、只是省略更新资产 | CI 缺少私钥时明确失败，避免产生缺少更新清单的稳定版发布 |
| 手动触发构建当前分支，却使用用户输入的其他 tag | 先验证已存在的稳定标签，再 checkout 标签对应的代码；同步应用版本及两个锁文件；校验草稿资产完整性 |

产物及安装模式依据 [Tauri 2 Updater 官方文档](https://v2.tauri.app/plugin/updater/)；Windows 退出语义另外核对了 Cargo.lock 锁定的 `tauri-plugin-updater 2.11.0` 源码。注册项依据 [Tauri NSIS 安装器模板](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi)。

## 2. 范围与版本

- 发布通道：Windows x86_64 稳定版；NSIS `currentUser` 安装和独立 portable exe。
- 用户主动从「帮助 → 检查更新…」或关于对话框发起；不后台自动安装。
- 已安装的 release 构建允许应用内升级。debug、便携版、其他安装形态和不支持的平台仅显示手动下载路径。
- 使用 semver 的版本优先级比较，严格大于当前版本才提示；忽略 build metadata 的差别，不接受候选预发布版本。
- CI 标签仅接受 `vX.Y.Z`，拒绝前导零、后缀、预发布与超出 Windows 字段范围的版本。支持预发布需要另行设计通道。
- 发布以标签为权威，`scripts/release.mjs sync` 同步 `package.json`、`package-lock.json`（含根 package）、`src-tauri/tauri.conf.json`、Cargo.toml 和 Cargo.lock 中应用包的版本，不改依赖版本。
- 应用显示使用编译元数据 `getVersion()` / `app.package_info().version`。开发时仍须维护仓库内版本一致。

## 3. 更新通道与安全边界

检查入口：`https://github.com/whoarei/remote-runner/releases/latest/download/latest.json`。

清单由 tauri-action 生成，示例（实际资产名称以 Release 为准）：

```json
{
  "version": "0.3.0",
  "notes": "更新说明",
  "pub_date": "2026-09-12T00:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "<签名文件内容，不是 .sig 地址>",
      "url": "https://github.com/whoarei/remote-runner/releases/download/v0.3.0/Remote.Runner_0.3.0_x64-setup.exe"
    }
  }
}
```

检查由 Rust 调用官方插件完成，超时 30 秒。网络失败、404、清单无效、缺少平台数据等显示检查失败，同时保留固定下载页入口；不能把这些情况显示为「已是最新版本」。草稿发布尚未公开，旧 Release 没有 latest.json，也可能造成检查失败。

Rust 进一步限制安装资产为 HTTPS、固定仓库、对应版本标签下的 `*-setup.exe`，签名字段不能为空。检查结果缓存插件 Update（含 URL、签名和版本），安装不重新请求 latest，因此不会静默换成另一个版本。新检查开始即清除旧缓存；应用重启后需重新检查。

下载超时 10 分钟。插件下载完整包到内存并验证 minisign 签名，验证成功才交给安装入口，安装时由插件写临时文件；不是流式落盘，也不做差量更新。当前全量 Windows 包适合这一方式，若未来产物显著增长应重新评估内存占用。

公钥保留在 `tauri.conf.json` 并编译进应用；私钥通过 `TAURI_SIGNING_PRIVATE_KEY` 注入 CI，口令通过 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 注入。仓库已有公钥不在本次修改中轮换，不生成或提交新的私钥。

签名保证安装包字节的真实性与完整性，**不签署 latest.json 的版本号和 notes**，也不替代 Windows Authenticode。它不能防止更新不可用或被阻断，也不应被描述为能抵抗掌握 CI 签名凭据的攻击者。当前方案信任 GitHub 发布元数据；若要求抵抗元数据篡改或旧签名包重放，应引入签名元数据及版本绑定协议。

## 4. 安装形态与生命周期

### 4.1 安装形态识别

当前通道仅发布 currentUser NSIS，与打包配置保持一致。release Windows x86_64 构建读取 HKCU 的 32/64 位注册表视图：

`Software\Microsoft\Windows\CurrentVersion\Uninstall\Remote Runner`

读取 `InstallLocation` 与 `UninstallString`，去除 NSIS 外层引号，对现存路径做 canonicalize，并要求：

1. 当前 exe 与注册目录下 `remote-runner.exe` 为同一路径；
2. 注册卸载程序与目录下 `uninstall.exe` 为同一路径且文件存在。

支持自定义安装目录；仅把 portable 放入 Programs 文件夹不会被判成安装版。无法识别、注册项过期、文件被改名等都退回手动路径。该判断用于选择安装方式，不作为可信代码认证；认证由签名完成。未来支持 perMachine 时须同步扩展安装器配置、注册表范围与验收。

### 4.2 安装保护

- 前端在开始前检查未保存文档、加载/保存/工作区变更/启动操作；显示具体原因，请用户先完成操作或保存。
- 活动任务（preparing、syncing、running、stopping）存在时拒绝安装，不擅自停止设备任务。
- `UpdateState` 的异步锁保证检查/安装只有一个在进行；另一个读写门控与 `run_script` 协作。任务启动持读锁直至 RunManager 登记完成；安装持写锁后检查活动任务，并持续持有直到失败或进程退出，消除「检查无任务后又启动」的竞态。
- 安装失败以 RAII 释放门控，恢复正常操作；同时提供手动下载。
- 下载/验签/安装期间关于对话框保持模态，禁止关闭按钮、Esc 和点击外部关闭；窗口关闭保护也检查 updating 状态，防止中途继续编辑并丢失修改。
- 前端先完成进度订阅再发起安装；监听失败不会开始下载；安装结束或失败释放监听。重复点击不会重复注册安装。

### 4.3 Windows 安装流程

1. 用户点击「下载并安装（将重启应用）」；后端再次核对安装形态、缓存版本和运行状态。
2. 下载并以 `app-update://progress` 事件上报字节数（最多约每 100ms 一次，末块在总量已知时必报）；总大小未知时显示不定进度。
3. 显示验签状态；失败保持当前应用并提供重试和下载页。
4. 验签后显示「正在启动安装程序」，插件以 passive 模式（有安装进度窗口）启动 NSIS，并退出当前进程。
5. NSIS 执行覆盖，完成后通过插件提供的重启参数重新打开应用；前端没有「安装成功返回后 relaunch」步骤。

插件成功启动安装程序后当前进程已经退出，无法继续捕获安装器后续的取消或失败；不能承诺所有安装错误都能在旧应用内回退。遇到此类问题使用下载页手动重装。V1 不提供下载取消或恢复断点。

## 6. 发布流程

1. 使用已存在的稳定标签，CI 精确 checkout 标签。相同标签的发布串行执行，避免互相覆盖。
2. 安装依赖，确认签名私钥存在；不存在则明确失败，不发布不完整的升级版本。
3. 同步版本及锁文件，运行前端与发布脚本测试。
4. `tauri-action@v0` 使用文件配置 `src-tauri/tauri.release.conf.json` 开启 `createUpdaterArtifacts`，构建 NSIS、签名、生成更新说明和 latest.json，上传到 draft Release。避免 PowerShell 内嵌 JSON 引号问题。
5. 上传 portable exe。读取草稿 latest.json 与资产列表，验证版本、URL、签名字段、NSIS exe / .sig / portable 存在且非空；缺失即 CI 失败，草稿仍不公开。
6. 发布者完成下面的真实升级验收后发布草稿，并确认该版本被 GitHub 选为 Latest。只有此时公共 latest 下载入口才能看到新清单。

本地常规构建不合并 release 配置，因此不需要签名私钥。发布格式须持续保持 Tauri 2 NSIS exe，不能只上传 portable 或漏掉 latest.json。安装器 productName、binary name、bundle identifier、安装模式、公钥应保持兼容。

## 7. 验证与部署边界

自动化验证覆盖：稳定 semver 比较（含相等、回退、预发布和 metadata）、包地址限制、缓存版本不匹配、注册路径与便携文件识别、运行/安装互斥释放、未保存修改及全部活动任务状态、订阅失败与错误清理、标签输入、版本/锁文件同步、发布资产缺失。

执行 `npm test`、`npm run build`、`cargo fmt --all -- --check`、`cargo test --offline --all-targets` 和 `git diff --check`；另用 `cargo check --offline --release --lib` 编译仅在 release 启用的注册表识别代码。

本次结果：前端 41 项通过；Rust 63 项单元测试和 5 项 SSH 本地集成测试通过，7 项 WSL 集成测试按约定跳过；前端构建、Rust 格式与 release 编译检查通过。首轮既有工作区文件替换测试出现 Windows 错误 1175，未修改该模块，单独复测及随后全量复测均通过。前端构建仍提示部分 chunk 大于 500 kB，不影响构建成功。

部署仍需在实际发布环境完成以下验收，本地单元测试不能替代：

1. 确认 Secrets 中私钥与现有编译公钥配对，口令正确，私钥有离线备份；未确认当前私钥口令状态，不假设为空。
2. 生成包含 `*-setup.exe`、`.exe.sig`、portable、latest.json 的签名草稿；核对清单签名与产物签名，并验证已发布稳定版本的公共入口可读取。
3. 在独立 Windows 测试环境，从包含本功能的版本升级到更高版本，验证默认目录、自定义目录、覆盖、重启、新版本号与配置保留；无升级能力的旧版本须先手动安装一次。
4. 验证便携 exe、同版本、404/离线、下载中断、错误签名、活动任务、未保存文件、重复点击及安装器后续失败情形。

本次不自动配置 GitHub Secrets、推送标签、发布 Release 或覆盖当前开发环境的安装。SSH/串口无实物验证；WSL 集成测试保持项目约定的显式 opt-in。
